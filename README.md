# ANVIRA — integration development build 1.2

Premium green/ivory customer and professional apps for iPhone and Android, with responsive Owner and Customer Care workspaces. This package includes working integration code and a runnable demo. **It is not yet a signed, deployed production release, and zero bugs cannot be guaranteed.**

## Open on your Mac in Codex

Extract the archive and run `START-MAC.command` from the extracted project. It creates `~/Desktop/ANVIRA`, preserves any existing folder by choosing a timestamped destination, opens Codex (or Finder if Codex is unavailable), installs the locked dependencies, checks the code and starts the demo. Node.js 24+ must already be installed. The launcher was syntax-checked here; actual macOS execution remains unverified because this workspace is remote Linux. See `CONTINUE-IN-CODEX.md` and `docs/ACCOUNTS.md` for continuity and account setup. The launcher never creates cloud accounts or stores the Google account password.

## Run locally

Node.js 24+ and npm are required for the local SQLite demo.

```sh
npm ci
npm run preview
```

Open http://localhost:4000. Customer, Professional, Owner and Customer Care share a temporary/sample service catalog and persisted local demo database. Generated builds are excluded from this source archive. `npm run preview` generates `dist/` before starting the API; `npm run api` alone does not build the web app. Remove only the local `server/anvira.sqlite*` files to reset sample data. Demo sessions are in memory and require signing in again after a reload/restart.

For native development, run `npm run api`, set your device's reachable `EXPO_PUBLIC_API_URL` in `.env`, then `npm start`. Android emulator: http://10.0.2.2:4000; iOS simulator: http://localhost:4000. Physical phones need a reachable LAN/HTTPS URL. Firebase native authentication requires an **Expo development build**, not Expo Go. Native code is generated by Expo configuration; `ios/` and `android/` are intentionally not hand-authored.

## Implemented in this revision

- Firebase Google and email/password authentication across customer, professional and staff workspaces; customer registration and password reset. Phone authentication is removed. Native SDK sessions; browser HTTP-only sessions compatible with Firebase Hosting, session-bound CSRF and origin checks. Claims and server records control Owner/Care access; the client cannot select a production role.
- Firestore transactional reservations with locks for service duration plus travel time, retry-safe writes and checkout idempotency. SQLite remains a separate demo option. Production refuses demo authentication and simulated payments.
- Razorpay server orders, hosted secure checkout, exact amount/currency/order verification, callback HMAC and signed payment/refund/payout webhooks. Payment capture, assignment, acceptance, service completion and financial settlement remain separate states.
- Expired reservation cleanup, reassignment after acceptance deadlines, full refund jobs for unfulfilled paid bookings, late capture recovery, outbox leases and reconciliation for uncertain provider outcomes. Unknown financial outcomes are not blindly retried.
- Saved address create/edit/remove, profile editing, promotion quotes/redemption, booking history pagination and older booking detail retrieval. Slot selection uses server availability and Indian Standard Time.
- Professional application, service skills/coverage, private identity and skill uploads, Owner verification/rejection, in-house/partner employment type, availability, working days/times and days off.
- Professionals can switch between their work dashboard and personal customer bookings without changing their server-verified account permissions.
- Net partner earnings with commission snapshots, held withdrawal balances, tokenized payout accounts, Owner approval/rejection and payout history. Live RazorpayX withdrawals default to disabled until approved credentials and static allowlisted egress exist.
- Complete service editing, add-ons, activation and Telugu service name/description fields; promotions; company policies/coverage/commission settings; Customer Care accounts and disable/re-enable controls.
- Support replies and resolution, notifications and read state, optional native push registration/delivery receipt checks, logout token deactivation, audit records and date-range CSV export with formula escaping.
- Account deletion/anonymization, private document cleanup and identity cleanup jobs, production rules denying direct datastore/storage access, request limits, structured errors and safe logging.
- Firebase Functions/Hosting/rules/indexes staging, Expo/EAS build profiles, configuration validation, Owner bootstrap, inactive catalog seeding, CI, runtime dependency compatibility patch and expanded English/Telugu UI copy.

## Additional work in 1.2

- Complete-history server aggregation replaces dashboard totals based on the latest 200 bookings. Owner date-range analytics include every matching booking in a range up to 366 days. Care receives operational counts, without financial sums. Reports describe booking cohorts/current payment status, not bank settlement or accounting profit.
- Professionals, support threads, Care accounts, earnings, payouts, notifications and audit records have forward/backward pagination. Professional name/skill filtering is explicitly scoped to the current page. General full-text search across all historical records is not implemented.
- Customer/professional booking conversations support replies, retry-safe message submission, pagination, assignment-based access and staff support access. Cancelled bookings are read-only; post-service sending closes after seven days. Message content is removed on sender account deletion and expires after 30 days (subject to scheduled cleanup). This is text messaging with explicit refresh and refresh on app updates, not sockets, phone calls or attachments.
- Authenticated HTTP quotas are per verified account, with a separate broader network limit. Production mutation quotas still use the datastore.

## Verification

See `evidence/verification.json` and `evidence/ui-results.json` for the final recorded results. API/provider tests use isolated databases, fake verified identity responses and simulated provider transport; **they do not prove completed Google account sign-in on physical devices or bank settlement works**. Firestore tests use the actual Firestore emulator and SDK, including concurrent reservation conflicts and denied client writes.

```sh
npm run check                 # strict TypeScript, lint, API/security/business tests
npm run export:web
npm run test:ui               # owns a temporary API/database; uses dist/
npm run test:firestore        # Firebase CLI and Java 21+ required
npm run export:all            # iOS/Android/web JavaScript/Hermes compilation
npx expo-doctor
```

On Linux the browser suite uses packaged headless Chromium; elsewhere install Playwright Chromium or set `CHROMIUM_EXECUTABLE`. There are no live charges or messages in these tests.

Use [docs/PRODUCTION.md](docs/PRODUCTION.md) for configuration, deployment, secrets, launch gates and known limits. `.env.example` contains names/placeholders only. ## Design source

The original editable local design exports supplied the emerald/forest/ivory palette, Manrope/Telugu typography, icons, living-room illustration and key page structure. `reference/` contains selected source exports. The earlier Figma file had foundations, not all 173 layouts. This revision does **not** claim every earlier screen is implemented pixel for pixel. The added operational views use the same design system.

On supported iOS versions, navigation uses native Liquid Glass; older iOS uses blur and reduced-transparency settings/Android/web use solid surfaces. Glass appearance, gestures, keyboard behavior, VoiceOver/TalkBack and performance need physical-device checks. The home glyph is a temporary launcher icon; final company artwork still needs selection. Telugu copy and translated service/policy content need a fluent human review.

## Structure

`src/app/` routes; `src/components/` screens/shared UI; `src/lib/` sessions/models/translations/vectors; `server/` API/domain/stores/gateway/workers; `tests/` isolated tests; `deployment/` Functions entry/features; `scripts/` staging/release helpers; `docs/` launch instructions; `reference/` original design samples; `evidence/` checked screenshots/results. `functions/` is a generated deployable copy, refreshed by `npm run stage:functions`.

## Isolated customer review

Run `./RUN-DEMO.command` or `npm run demo` with Node 24, then open `http://localhost:4001/?sample=customer`. This builds the sample app separately and signs into its customer demo. Profile → Sign out opens the role chooser. The live Firebase environment stays in `.env`; sample records use `server/review-demo.sqlite`.
