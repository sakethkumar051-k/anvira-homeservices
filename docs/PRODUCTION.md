## Environment split

Copy `.env.example` to ignored `.env`. Local live API uses `APP_MODE=firebase`, `PAYMENT_MODE=razorpay` and Application Default Credentials. On Google Functions use the function's service identity and narrowly scoped IAM, not a downloaded service-account key. Set `NODE_ENV=production`, explicit `ALLOWED_ORIGINS`, and HTTPS `PUBLIC_API_URL`/`WEB_APP_URL`. `TRUST_PROXY` must match the actual deployment; Functions uses one proxy hop.

For the client set `EXPO_PUBLIC_AUTH_MODE=firebase`, the API URL and public Firebase/EAS values before building. Browser deployments should use the same origin for the app and API so the HTTP-only session stays first-party. Native uses Firebase ID tokens. The server verifies revocation and checks a matching signed staff claim plus active staff record.

Google and Email/Password are enabled for all roles. Phone sign-in is removed and its Firebase provider remains disabled. Configure authorized web domains and native Google OAuth IDs, register EAS/Google Play Android signing fingerprints, and use a signed development build. New registrations are customers; approved server records and claims control staff access. Staff and sensitive account/bank changes may require signing in again within five minutes. Google/email authentication can use Spark; Cloud Functions and Cloud Storage require a billing-enabled project if those services are used. No billing plan was changed. See `docs/AUTH-UPDATE.md`.

## Firebase deployment preparation

1. Create staging and production resources with the intended data location. Enable Firebase Auth, Firestore Standard, private Storage and billing as required by the selected services. Configure a dedicated runtime identity with only the required Firestore, Storage signing/object and Firebase Auth administration rights. Signed document URLs need IAM permission to sign blobs as well as read objects.
2. Set the root public environment values and the Functions non-secret parameters `PUBLIC_API_URL`, `WEB_APP_URL`, `ALLOWED_ORIGINS`, `FIREBASE_STORAGE_BUCKET`. Firebase CLI can prompt for these or read an ignored `functions/.env.<project-id>`. Do not commit that file.
3. Enter payment values through `firebase functions:secrets:set RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET`. These are the only bound payment secrets with default deployment features. Configure their values through the CLI's secure prompt rather than command-line arguments.
4. `deployment/features.json` defaults to `payouts:false` and `enhancedPush:false`. To enable approved RazorpayX, set payouts true, configure the four `RAZORPAYX_*` secrets and a static NAT egress VPC connector, allowlist its fixed public IP with RazorpayX, and set `VPC_CONNECTOR` in the deployment environment. Functions refuse to export payout-enabled configuration without the connector. A connector name alone does not prove its egress IP is static; verify NAT and provider connectivity in staging. Enhanced Expo push security additionally needs its project setting and `EXPO_ACCESS_TOKEN` bound secret.
5. Run `npm run check:release`, `npm run stage:functions`, and build the live web output. Firebase Hosting predeploy validates public config and rebuilds the web app. Deploy reviewed Functions, indexes, deny-client Firestore/Storage rules and Hosting to **staging first**, specifying the project explicitly. Deployment is not performed by this handoff.
6. Bootstrap an existing verified Owner: `APP_MODE=firebase node scripts/bootstrap-owner.mjs <owner-uid>` under authorized ADC. Sign in again afterward. Optional `npm run seed:catalog -- --confirm-inactive-samples` adds inactive catalog examples only, refuses duplicate documents, and never seeds production professionals/published policies. Replace scope/prices/localized content before activation.
7. Through Owner settings publish real policies/URLs/support phone, coverage and commission. Add Care staff; the API returns a private password setup link. Share it through a trusted channel yourself; no automatic staff invitation email is sent by this package.
8. Register `/api/webhooks/razorpay` for captured/failed payments and created/processed/failed refunds. Use `/api/webhooks/razorpayx` with its separate secret for payout lifecycle events if enabled. Verify raw-body HMACs, event retries and provider dashboard reconciliation in staging. Configure capture behavior and confirm the exact payment amount/currency/order before fulfillment.

The generated Functions runtime is Node 22, region `asia-south1`, 512 MiB, minimum zero API instances and maximum three. Maintenance runs every five minutes with one scheduled instance. These are launch defaults, not load-test results or a guaranteed spending cap. Fixed egress networking introduces additional resource costs; leave it disabled until partner withdrawals require it.

## Financial behavior and recovery

Prices are server-calculated in whole rupees and provider requests use paisa. Bookings preserve service/add-on/discount and commission snapshots. Failed/expired unpaid reservations release capacity and reserved offer usage. Captured money is assigned only to a qualified approved professional. Professional acceptance is separate; an unaccepted assignment is offered to another eligible professional at the configured deadline, then an unfulfilled paid booking creates a full refund job. The five-minute worker cadence can delay a deadline action by up to that interval.

Refund/payout requests occur outside Firestore transactions. Jobs acquire leases and store provider identifiers. Duplicate captures/events and withdrawal retries do not create duplicate ledger credits/settlements. Ambiguous provider failures are marked `needs_reconciliation`. The Owner must identify the provider record and verify it through Payouts & reconciliation; refunds are not blindly resubmitted. Known provider identifiers are polled as well as updated by signed webhooks. Reversed payouts restore balance once. Exceptional terminal-state contradictions require accounting review.

RazorpayX is optional and its account approval/IP allowlisting is separate from ordinary Razorpay Checkout. In-house compensation is administered by ANVIRA; the app's withdrawable wallet is for partners. A professional's employment type cannot change while active jobs or unsettled partner balances remain.

## Operations, cost and retention

Set billing budget notifications at agreed thresholds and enable alerts for 5xx errors, sustained latency, failed scheduled jobs, aged unassigned bookings, aged pending refunds/payouts, reconciliation jobs and push failures. Budget notifications are alerts, not a hard service-spending cap. Enable Firestore scheduled backups/PITR if appropriate, document retention, storage lifecycle rules and an actual restore rehearsal. Keep production and staging data isolated. No backups, budget alerts, IAM grants, NAT resources or monitoring alerts have been created without project access.

The client refreshes after writes, when returning to the app/window, and every three minutes while active; background polling is suppressed. Push workers use leases, bounded retries and receipt checks. In-app notifications remain available without push. Push is at least once; duplicate delivery is possible if a worker crashes after sending but before recording success.

## Known limits and remaining release gates

- Google account completion on devices, provider checkout/refunds/payouts, Storage signed URLs and APNs/FCM delivery are coded but remain untested against your accounts. Emulator/fake transport tests do not substitute for those checks.
- Dashboard totals and seven-day activity are calculated through server aggregation across the full booking history. Owner reports support date ranges up to 366 days and show booking creation cohorts with current payment status; these are not bank settlements or accounting profit. Aggregates are separate queries, not a single accounting snapshot. CSV exports still reject 1,000-row ranges so they can be split. Booking browsing and staff/professional/support/notification/ledger/payout/audit views have pagination. Professional filtering searches only the current page; complete historical full-text search and large-scale load tests remain open. The state bootstrap lists remain bounded, while dedicated list views retrieve later pages.
- The eligible assignment scan is bounded to 200 approved professionals. Launch staffing should remain below that bound; a larger marketplace needs indexed region/skill candidate queries and ranked capacity selection. High-volume account deletion exceeding transaction limits requires assisted processing; the API rejects it rather than partially deleting records.
- Fulfilled-service refunds initiated directly in the provider dashboard, disputes, chargebacks, partial refunds, GST/tax invoices, payroll, bank verification/KYC beyond provider/account onboarding, customer-professional phone calling, messaging attachments/read receipts/socket updates, and fraud investigations are not automated in this build. Decide the business requirements before exposing those flows. Credentials alone do not resolve them.
- Fluent Telugu review, real service/policy translations, accessibility/device testing, final branding and full screen-by-screen design approval remain open. The original 173 layouts are not all mirrored exactly.
- `evidence/dependency-audit.json` retains the package audit. The vulnerable gRPC dependency was pinned to 1.14.5. The legacy Router URI decoder received a reproducible CommonJS bounded-decoding patch with tests; npm still flags its upstream package version. Unpatched upstream `braces`/`node-forge` build-tool advisories and legacy UUID advisories require release security review or an appropriate SDK/tooling update. Do not use `npm audit fix --force` to downgrade Expo as its suggested range implies. No claim of a clean dependency audit is made.
- The deployable Functions package uses a narrower dependency set and pinned direct versions; confirm the deployed dependency lock/audit separately. Patch application is a required root `npm ci` postinstall gate.

## Booking conversations

Text messages are tied to a booking and the current assigned professional. Reassigned professionals lose access. Owner/Care can view and reply as ANVIRA Support; no private staff email is displayed as a sender. Requests are idempotent and capped at 1,000 messages per conversation. Cancelled bookings are read-only; completed booking conversations close to new messages after seven days. Message records expire after 30 days, with cleanup running in bounded maintenance batches. The API filters expired content immediately. Account deletion anonymizes the sender's message content; high-volume deletion remains assisted. Approve and publish this retention/support-access policy before launch. Calling, attachments, read receipts and socket delivery are not implemented.
